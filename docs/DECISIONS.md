# 关键决策记录

按主题记录当前生效的关键决策. 编号固定, 未使用的编号不复用.

## ADR-001 DOCX 转 Markdown 使用 pandoc + panflute

背景:

- 需要把 Word 需求文档转成 agent 可读结构.
- 手写 DOCX 解析器维护成本高.
- 需要保留标题编号, 表格, 图片, 附件.

决策:

- pandoc 负责 DOCX -> AST -> GFM.
- panflute 负责 AST 修正.
- olefile + openpyxl 处理 OLE 和 Excel.

后果:

- 减少自写解析代码.
- 需要维护 pandoc 和 panflute 依赖.
- 复杂表格和标题编号仍需要自定义规则.

## ADR-003 部门最多 5 级

背景:

- 原需求写"最多 6 级".
- 部门编码 10 位, 每级 2 位, 只能支持 5 级.

决策:

- 按 5 级实现.
- 编码规则: 每级 2 位, 共 10 位.

后果:

- 与原文"6 级"不一致, 需要在需求澄清时确认.
- 编码规则简单可控.

## ADR-005 签名存 base64

背景:

- 存 `signature_image`.

## ADR-007 私有源码 + 公有密码压缩包

背景:

- 源码仓库需要保持私有.
- 需要一个公有的分发位置.

决策:

- 私有源码仓库: `hr-manager-sys`.
- 公有 Release 仓库: 只放密码保护的压缩包.
- 密码不写入仓库.

后果:

- 源码不公开.
- 分发依赖密码.
- 公有仓库需要手动维护.

## ADR-008 监控只做技术指标

背景:

- 业务指标需要在业务事件处埋点.
- 埋点会让 service 依赖 metrics, 业务逻辑和监控耦合.

决策:

- Prometheus 只采集技术指标: HTTP, JVM, 进程, HikariCP, health.
- 不在业务 service 中注入 metrics.
- 业务健康如果后续需要, 用独立只读 exporter.

后果:

- 业务代码保持干净.
- 业务健康趋势暂不可见.
- 需要业务健康时必须单独设计 exporter 和口径.

## ADR-009 admin 接口按路径鉴权

背景:

- 前端菜单隐藏不等于后端鉴权.
- 普通员工可能直接调用 admin 接口.

决策:

- `AuthInterceptor` 对 `/api/admin/**` 做权限校验.
- 路径映射到菜单 code.
- 未映射的 admin 路径默认拒绝.

后果:

- 员工和 HR 的访问边界由后端强制执行.
- 新增 admin 接口必须同步更新权限映射.

## ADR-010 生产关闭演示数据

背景:

- `DataInitializer` 会写入演示账号和演示考勤.
- 生产数据库如果为空, 会写入已知密码账号.

决策:

- 增加 `app.seed.enabled`.
- 默认开启, `application-prod.yml` 关闭.

后果:

- 生产首次部署需要自行创建管理员.
- 测试和开发仍可直接启动.

## ADR-011 企业微信只做应用消息推送

背景:

- 需求要求通过企业微信做考勤提醒和通知.
- 企业微信还有 SSO, 通讯录同步, 电子签名等能力.

决策:

- 只做企业微信应用消息推送, 站内消息保留.
- 企业微信异步发送, 失败不影响站内消息.
- 用户用 `wecom_user_id` 映射, 留空回退工号.
- 不做 SSO, 通讯录同步, 电子签名.
- 发送结果写 `wecom_message_log`.

后果:

- 覆盖提醒和通知需求.
- 企业微信故障不影响站内消息.
- 用户映射需要人工维护.
- 需要处理 token, 超时, 限流和失败日志.

范围说明:

- 需求还包含企微工作台员工自助、企微身份登录、电子签名和签字过程回溯, 本期不做, 见 [README TODO](../README.md#todo-未实现的需求).

## ADR-012 数据库使用 Flyway

背景:

- 原来维护 `schema.sql` 和 `schema-mysql.sql` 两份基线.
- 新增字段和表时容易漂移.

决策:

- 使用 Flyway 做版本管理.
- 迁移按数据库分目录: `db/migration/h2` 和 `db/migration/mysql`.
- `MigrationConsistencyTest` 校验版本和结构一致.
- MySQL 集成测试用 Testcontainers 真实执行迁移.

后果:

- 数据库变更有版本和顺序.
- 已应用迁移不能修改, 只能新增版本.
- H2 和 MySQL 迁移需要同步维护.

## ADR-013 统一使用 MySQL

状态: 已决定, 待实施.

背景:

- 当前 H2 开发 + MySQL 生产, 需要维护两份迁移.
- 已出现索引, 列长度和长文本类型漂移, 现有一致性测试覆盖不到.
- 测试运行在 H2, 无法暴露 MySQL 的排序, 字符集和严格模式差异.

决策:

- 所有环境统一使用 MySQL 8, 移除 H2 依赖和迁移目录.
- 迁移只保留 `db/migration/mysql`.
- 本地自动化测试使用本机 MySQL 的临时 schema, 每次运行新建, 启动时清理遗留.

详细方案:

- 见 [UNIFIED-MYSQL.md](UNIFIED-MYSQL.md).

后果:

- 只维护一份迁移, 不再有结构漂移.
- 本机需要 MySQL 才能开发和测试.
- 发布物不再免依赖运行, `java -jar` 需要可用的 MySQL.
