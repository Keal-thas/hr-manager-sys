# 业务数据模型

需求见 [REQUIREMENTS.md](REQUIREMENTS.md). 字段见 [FIELD-CONTRACT.md](FIELD-CONTRACT.md), 表结构见 Flyway 迁移.

## 1. 模型 (14)

| 域 | 模型 | 一句话 | 现状 |
|---|---|---|---|
| 考勤 | 考勤批次 | 一个年月一份, 管最新期和上传方式 | 有表 |
| | 考勤明细 | 年月 x 员工, 一人一条 | 有表, 指标在 `data_json` |
| | 处罚明细 | 年月 x 员工, 可多条 | 有表 |
| | 签字证据 | 承诺, 签名, 线下图片或 PDF | **内嵌**在考勤明细 |
| | 签字过程记录 | 回溯 | **缺** |
| 触达 | 通知 | 标题, 正文, 发送范围 | 有表 |
| | 发送对象 | 发给谁, 发送时固化 | **内嵌**为文本 |
| | 用户消息 | 每人一条, 管已读 | 有表, 通知和考勤提醒共用 |
| | 企微投递记录 | 成功, 失败, 跳过 | 有表 |
| | 通知模板 | 可复用的标题和正文 | 有表, 缺创建人和修改人 |
| | 通知附件 | 入职资料及签收 | **缺** |
| 主数据 | 员工 | 以工号为唯一标识 | 有表 |
| | 部门 | 树, 最多 5 级 | 有表 |
| | 角色 | 一组菜单权限 | 有表 |

## 2. 关系

```text
员工 --工号--> 考勤明细 --> 签字证据 --> 签字过程记录
考勤批次 --> 考勤明细
考勤批次 --> 处罚明细 (按工号对应, 一人一月多条)
通知模板 --> 通知 --> 发送对象, 通知附件
考勤明细, 通知 --> 用户消息 --> 企微投递记录
```

关联键是工号, 不是用户 ID.

## 3. 关键规则

- **批次**: 年月唯一, 不晚于当前. 最新期是年月最大的, 不是最近上传的.
- **考勤明细**: 批次内工号唯一. 状态 未阅读, 已阅读, 已确认. 姓名和部门是快照, 部门以系统为准, 改名或注销不影响历史. 用户注销后记录和签字保留.
- **导入**: 指标不计算, 小数 6 位, 出错整批取消. 指标清单见 `field-dictionary.csv`.
- **处罚**: 新增生成编号 (工号加两位月份加三位流水), 修改按编号匹配. 工号必须在当月考勤中.
- **签字**: 勾选承诺加手写签名. 线下补签仅限历史期. 一条明细保留一份有效证据.
- **通知**: 发送对象发送时固化. 进详情页即已读. 消息保存发送时快照.
- **企微消息对象**: 新增或覆盖发清单中所有人; 增量发新增的人"已生成", 被改的人"已调整"; 考勤提醒发未阅读和未确认的; 异常提醒发未阅读且有处罚的. 历史期不发.

## 4. 开发自定

存储形态, 签名存放位置, 防重复提交, 推送实现. 业务以后若要按指标筛选或做报表, 才需要拆列.

## 5. 待确认

按重要性排序.

1. **回溯记什么**: 笔迹, 时间, 视频, 保留多久.
2. **覆盖或增量后是否重签**: 需求文案是"已调整, 请尽快签收", 倾向重签 (推断).
3. **入职资料**: 要不要附件, "签收"是已读还是单独确认.
4. **是否保留调整历史, 阅读和确认的时间点**: 需求未写, 但目的要求可溯源 (推断).
5. **FL 和 D0 的公式**: 名称像公式, 冲抵规则没给, 现按导入值存.
6. **工号能否修改**: 它是考勤关联键.
7. **部门通知是否含下级部门**.

次要: 通知是否有重要程度和发布部门字段; PC 只看当月而企微看最新期; 考勤文案有两套; 部门 5 级 (需求写 6 级, 见 ADR-003); 缩略语未定义.
