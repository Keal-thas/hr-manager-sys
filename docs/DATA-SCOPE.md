# 领域模型

需求见 [REQUIREMENTS.md](REQUIREMENTS.md). 本文只讲领域和领域之间的关系, 不列字段. 字段见 [FIELD-CONTRACT.md](FIELD-CONTRACT.md) 和 `field-dictionary.csv`.

## 1. 三个领域

```text
主数据 (部门, 员工, 角色)
   ^ 按工号引用                    ^ 按用户和部门引用
考勤 (批次, 明细, 处罚, 签字证据) --考勤事件产生消息--> 通知触达 (通知, 用户消息, 企微投递)
```

## 2. 领域之间怎么关联

| 关系 | 怎么对应 |
|---|---|
| 考勤 -> 主数据 | 明细按**工号**对应员工. 姓名和部门在导入时拷贝, 之后不再跟随主数据变化 |
| 考勤 -> 通知触达 | 上传和提醒时给员工写用户消息, 消息里记批次 ID |
| 通知触达 -> 主数据 | 通知的接收人是员工, 发送范围可以按部门 (含下级) |
| 考勤内部 | 批次 -> 明细 -> 签字证据; 批次 -> 处罚 (按工号对应明细) |
| 通知触达内部 | 通知 -> 用户消息 (消息里记通知 ID) -> 企微投递 (按用户对应) |
| 主数据内部 | 部门成树; 员工属于一个部门和一个角色 |

表之间没有物理外键, 关联全靠应用层.

## 3. 概念落在哪

14 个概念, 10 张表. 2 个内嵌在别的表里, 2 个不存在.

| 领域 | 概念 | 落地 |
|---|---|---|
| 考勤 | 考勤批次 | 表 `attendance_batch` |
| | 考勤明细 | 表 `attendance_record` |
| | 处罚明细 | 表 `attendance_penalty` |
| | 签字证据 | **内嵌**在考勤明细里 |

## 4. 系统怎么动

- **明细状态**: 未阅读, 员工打开变已阅读, 员工签名变已确认. 历史期可由管理员补签直接变已确认.
- **上传**: 新增, 覆盖, 增量三种.
  - 覆盖只限最新期, 会**删除该批次全部明细和处罚后重建, 已确认的签名随之丢失**.
  - 增量按工号新增或更新; 已确认的明细被改数据后**仍保持已确认, 旧签名还在**.
- **产生消息**: 上传和提醒都给涉及的员工写用户消息, 历史期的增量除外. 提醒只限最新期.
- **通知**: 范围是全员, 部门 (含下级), 指定员工; 每个接收人一条用户消息.
- **企微**: 每条用户消息写入后, 若已启用, 异步推送并记录结果.

## 5. 现状缺口

- 没有阅读时间, 确认时间只有签名时间.
- 没有考勤调整历史, 覆盖是物理删除.
- 确认接口不校验是否最新期.
- 通知模板没有创建人和修改人.
- 签字过程记录, 通知附件不存在.

2. 回溯记什么, 保留多久.
3. 入职资料要不要附件, 签收是已读还是单独确认.
4. FL 和 D0 的公式: 现按导入值存.
5. 工号能否修改: 它是明细和员工的关联键.
6. 部门通知含下级: 现状含.
