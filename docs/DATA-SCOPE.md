# 领域模型

需求见 [REQUIREMENTS.md](REQUIREMENTS.md). 本文只讲两个关键领域和它们的关系, 不列字段. 字段见 [FIELD-CONTRACT.md](FIELD-CONTRACT.md).

## 1. 两个关键领域

9 个关键概念: 5 个有表, 2 个内嵌在别的表里, 2 个不存在.

### 考勤处罚

```text
考勤批次 -> 考勤明细 -> 签字证据
考勤批次 -> 处罚明细   (按工号对应明细)
```

| 概念 | 是什么 | 落地 |
|---|---|---|
| 考勤批次 | 一个年月一份, 标出最新期 | 表 `attendance_batch` |
| 考勤明细 | 年月 x 员工, 一人一条, 带确认状态 | 表 `attendance_record` |
| 处罚明细 | 年月 x 员工, 可多条 | 表 `attendance_penalty` |
| 签字证据 | 员工确认的凭证 | **内嵌**在考勤明细里 |
| 签字过程记录 | 回溯 | **不存在** |

这里的"确认"是签字, 强凭证.

### 通知确认

```text
通知 -> 用户消息    (每个接收人一条, 已读即确认)
通知 -> 通知附件    (不存在)
```

| 概念 | 是什么 | 落地 |
|---|---|---|
| 通知 | 管理员发布的一条, 带发送范围 | 表 `message_notice` |
| 发送对象 | 全员, 部门, 指定员工 | **内嵌**: 条件在通知里, 实际接收人就是用户消息 |
| 用户消息 | 每人一条, 已读即确认 | 表 `sys_message` |
| 通知附件 | 入职资料文件及签收 | **不存在** |

这里的"确认"是已读, 弱凭证. 需求目的里入职资料要"签收", 现在只有已读.

### 两个领域的交汇

考勤的催办也写进用户消息. 用户消息是共用的收件箱, 用类型区分来源, 并记下对应的批次或通知.

## 2. 支撑

- **员工, 部门, 角色**: 考勤明细按工号对应员工; 通知可按部门发送.
- **企微**: 每条用户消息写入后异步推送, 结果记在投递记录里, 失败不影响站内消息.
- **通知模板**: 可复用标题和正文, 与确认无关.

表之间没有物理外键, 关联全靠应用层.

## 3. 系统怎么动

**考勤处罚**

- 明细状态: 未阅读, 员工打开变已阅读, 员工签名变已确认. 历史期可由管理员补签直接变已确认.
- 上传分新增, 覆盖, 增量三种.
  - 覆盖只限最新期, 会**删除该批次全部明细和处罚后重建, 已确认的签名随之丢失**.
  - 增量按工号新增或更新; 已确认的明细被改数据后**仍保持已确认, 旧签名还在**.
- 处罚分新增和修改: 新增生成编号, 修改按编号匹配. 工号必须已在当月明细里.
- 上传和提醒都给涉及的员工写用户消息, 历史期的增量除外. 提醒只限最新期.

**通知确认**

- 发送范围: 全员, 部门 (含下级), 指定员工. 每个接收人一条用户消息.
- 员工打开详情即视为已读.

## 4. 现状缺口

- 考勤处罚: 没有阅读时间, 确认时间只有签名时间; 没有调整历史, 覆盖是物理删除; 确认接口不校验是否最新期; 没有签字过程记录.
- 通知确认: 没有阅读时间; 没有附件, 没有签收.

## 5. 待确认

**考勤处罚**

1. **覆盖和增量对已确认签名怎么处理**: 现状是覆盖清空, 增量保留旧签名但数据已变.
2. 签字过程回溯记什么, 保留多久.
3. FL 和 D0 的公式: 现按导入值存.
4. 工号能否修改: 它是明细和员工的关联键.

**通知确认**

5. 入职资料要不要附件, 签收是已读还是单独确认.
6. 部门通知含下级: 现状含.

次要: 通知是否有重要程度和发布部门; PC 只看当月而企微看最新期; 考勤文案有两套; 部门 5 级 (需求写 6 级, 见 ADR-003); 缩略语未定义.
